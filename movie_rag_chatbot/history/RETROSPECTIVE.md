# 📝 회고

## [바닐라 RAG 구현]

**배운 점**
- RAG가 검색(R) -> 증강(A) -> 생성(G) 구조라는 것을 직접 구현하며 이해했다.
    특히 임베딩 모델(검색)과 LLM(생성)이 서로 다른 역할을 하는 별개의 모델이라는 점, 검색은 텍스트를 벡터로 바꿔 유사도로 찾는다는 원리를 알게 됐다.
- 청킹, 메타데이터 태깅, 벡터 저장 같은 인덱싱 단계가 검색 품질을 좌우한다는 것을 체감했다

**어려웠던 점 & 해결**
- 위키백과 줄거리 수집이 라이브러리 불안정과 요청 차단으로 계속 실패했다.
    라이브러리 -> 공식 API -> 재시도 로직 순서로 원인을 좁혀가며 해결했다.
- ChromaDB가 구글 드라이브에서 손상되는 문제가 생겼는데 원인이 SQLite와 드라이브의 호환성 문제임을 파악하고 로컬 환경으로 옮겼다.
- 데이터가 부족해서 문제가 발생했다고 생각했는데 사실 검색을 못해서인 경우가 많았다.
    제목 인식 검색을 추가해서 특정 작품 검색 문제를 해결했다.

**깨달은 점**
- 처음에는 특정 장르 검색이 안 되는 이유가 하이브리드 검색을 적용하지 않아서라고 생각했다. 하지만 임베딩 모델을 무료 로컬 모델에서 Gemini 임베딩 모델로 바꾸니 검색 품질이 눈에 띄게 좋아졌다.
- 이를 통해, 검색 품질은 검색 방식 뿐만 아니라 텍스트를 벡터로 바꾸는 임베딩 모델의 성능에도 크게 좌우된다는 것을 알게 되었다. 좋은 검색 결과를 얻으려면 성능 좋은 임베딩 모델이 필요하다는 것을 직접 확인했다.

**아쉬운 점**
- 순수 의미 검색만으로는 장르 필터링이 정확하지 않아서 하이브리드 검색이나 리랭킹으로 개선할 여지가 있다.
- 답변 품질을 정량적으로 평가하지 못했다. (RAGAS 등)

**다음에 적용할 것**
- 검색 로직을 LangChain 리트리버로 마이그레이션하면서 하이브리드 검색도 함께 적용해볼 계획이다.

## [LangChain 마이그레이션]

**배운 점**
- 바닐라에서 함수로 직접 짰던 검색 -> 프롬프트 조합 -> 모델 호출 -> 텍스트 추출을 LangChain에서는 리트리버, 프롬프트, 모델, 파서라는 정해진 부품을 `|`로 이어붙인 체인으로 표현한다는 것을 이해했다.
- `|`는 앞 단계의 결과를 다음 단계로 넘긴다는 의미고, 바닐라에서 변수로 하나씩 넘기던 것을 자동화한 것임을 알게 되었다.

**느낀 점**
- 처음에는 LangChain 문법(`|`, RunnablePassthrough 등)이 복잡해 보였지만, 바닐라에서 개념을 먼저 학습하고 오니 같은 흐름을 더 짧게 표현한 것임을 알 수 있었다.
- 데잍를 그대로 재사용하고 검색과 답변 로직만 교체하면 돼서 파일을 역할별로 나눠둔 구조의 장점을 체감했다.

**깨달은 점**
- LangChain 버전에는 바닐라에 있던 제목 인식 검색과 스포일러 메타데이터 필터를 아직 옮기지 않았는데도, 특정 영화 검색과 스포일러 조절이 잘 동작했다.
- 원인을 분석해보니 2가지가 있었다.
    - 제목 검색: 임베딩 모델을 성능 좋은 Gemini로 교체해서 제목 필터 없이 순수 의미 검색만으로도 특정 영화를 잘 찾아냈다.
    - 스포일러 조절: 검색 단계에서 거르지는 않지만 시스템 프롬프트에 넣은 "명시적으로 요청할 때만 결말 포함"이라는 규칙에 따라 LLM이 스스로 스포일러를 조절했다.
- 같은 결과라도 구현 방식이 다른 것을 발견했다.
    - 바닐라: 검색 단계에서 메타데이터로 차단 (확실한 제어)
    - LangChain: LLM이 프롬프트 규칙으로 자제 (100%는 아님)
- 이를 통해 검색으로 제어, 프롬프트로 제어라는 설계 선택지가 있다는 것을 알게 되었다.

**다음에 적용할 것**
- LangGraph로 마이그레이션 후 AI Agent로 확장
- LangSmith Dataset 기반 정량 평가 - 최종 버전에 적용 예정
- 하이브리드 검색, LangSmith를 통한 체인 추적 및 평가
- 스포일러를 프롬프트 규칙이 아닌 메타데이터 필터로 더 엄격하게 제어

## [LangSmith 활용]
- LangSmith로 체인 실행을 추적하며 검색(retriever)이 실제로 어떤 영화 조각을 가져오고, 그것이 프롬프트에 어떻게 반영되는지 단계별로 확인할 수 있었다.
- 제목 필터가 없어도 특정 영화를 잘 찾는 현상을 추적 로그로 직접 검증할 수 있었다.
- 코드 내부를 눈으로 보니 동작의 원인을 이해하기 쉬웠다.

## [LangGraph 마이그레이션]

**배운 점**
- LangGraph는 State를 노드들이 주고받으며 처리하고, 조건부 엣지로 분기하는 구조라는 것을 이해했다. LangChain이 직선 파이프라면, LangGraph는 판단해서 길이 갈리는 그래프라는 차이를 알았다.
- 스포일러 조절을 바닐라 RAG처럼 코드로 판단하는 대신 분류 노드에서 LLM이 판단하도록 구현했다. 판단 로직이 실행부(app_langgraph.py)에서 그래프 안으로 들어가면서 역할이 깔끔해졌다.
- 장르 추천은 의미 검색이 아니라 조건 검색으로 조절해야겠다는 판단에, 벡터 검색 대신 필터 + 평점순 정렬로 분리했다. 모든 검색을 벡터로 할 필요는 없다는 것을 알았다.

**어려웠던 점**
- 처음엔 내 개인 프로젝트 챗봇이 단순해서 굳이 LangGraph가 필요 없다고 생각했지만, 스포일러 유무에 따라 검색 방식을 분기하는 구조로 만드니 그래프를 쓸 이유가 생겼다.
- 제미나이 응답 형식(리스트/문자열)이 일정하지 않아 텍스트 추출을 별도로 처리해야 하는 문제가 있었다.

**다음에 적용할 것**
- 의도 분류(추천, 특정 작품, 잡담) 등의 분기도 추가해서 에이전트를 더 확장
- 분류 노드를 키워드 방식으로 바꿔 API 요청 수 줄여 한도 관리
- LangSmith Dataset 기반 정량 평가

## [FastAPI & 프론트엔드]
- RAG 로직을 `answer` 함수로 분리해둔 덕에, FastAPI는 이 함수를 호출하는 정도로만 만들면 됐다. 'CLI -> 웹 서버' 전환이 파일에 몇 줄 추가하는 것으로 실행되는 것을 보며 역할별 파일 분리의 이점을 체감했다.
- 프론트는 Streamlit으로 시작했지만 레이아웃을 원하는대로 수정하기 위해 바닐라 HTML/JS로 전환해서 바이브코딩했다.

## [스트리밍 & 배포]

**배운 점**
- 스트리밍과 비동기가 별개의 개념이라는 것을 알게 되었다. FastAPI의 StreamingResponse는 동기로도 동작해서 데모 규모의 프로젝트에서는 동기로도 충분하다고 판단했다.
- Docker가 실행 환경까지 컨테이너에 담기 때문에 Docker만 설치되어 있다면 어느 컴퓨터에서든 프로젝트를 실행할 수 있다는 것을 배웠다.

**어려웠던 점 & 해결**
- 서버에서 직접 친 코드와 로컬에서 수정한 코드가 깃허브에서 어긋나 pull할때 충돌이 있었다. 그래서 이후에는 로컬 수정 -> push -> 서버 pull -> 재시작 흐름으로 진행했다.
- 조원들한테 부탁해서 여러 명이 동시에 테스트하니 답변이 실패했다. 처음에는 동기 처리때문에 요청이 밀려서 생긴 문제라고 생각했는데, 로그를 확인하니 Gemini 무료 API 한도 초과(429)였다.

**깨달은 점**
- 겉으로 보이는 증상("서버 연결 실패" 문구)과 실제 원인(API 한도 초과)이 다를 수 있다는 것을 배웠다. 가능한 상황을 예상해 상황에 맞는 에러 메시지가 나오도록 수정이 필요하다.
- 외부 API에 의존하는 서비스는 내 코드에 문제가 없어도 외부 사정(한도/서버 사정)에 의해 실패할 수 있다는 것을 알았다. 따라서 재시도, 모델 분리같은 대비책이 필요하다는 것을 느꼈다.

**다음에 적용할 것**
- 스포일러 판단을 직접 학습한 모델로 전환해서 API 의존도 낮추기
- 프론트에서 에러 종류를 구분해서 더 정확한 안내 메시지 표시하기 (연결 실패 / 서버 혼잡 / 한도 초과 등)
- LangSmith Dataset 기반 정량 평가로 개선 효과를 수치로 검증하기
