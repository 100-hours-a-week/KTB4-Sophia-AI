# 🎬 Movie RAG Chatbot

스포일러 수위를 조절할 수 있는 영화 정보 검색 및 추천 챗봇 (RAG 기반)

## 💡 기획 배경

평소 쉴 때 영화를 틀어놓고 취미 생활이나 집안일을 하는 것을 좋아한다.
그런데 영화에 온전히 집중하지 못하다 보니, 중간중간 보면 내용이 이해되지 않아서 처음으로 돌아가 영화를 다시 보거나 아예 꺼버리는 일이 잦았다.
그래서 좋아하는 장르를 골라 검색하고, 줄거리를 미리 파악한 뒤, 편하게 감상할 수 있는 도구가 있으면 좋겠다고 생각했다.

처음에는 특정 장르 데이터만 다루려 했지만 데이터 양이 너무 적어서 전체 장르 검색으로 확장했다.

개인적인 용도를 넘어서도 쓸모가 있다고 생각한다.
요즘 스마트 TV는 음성으로 AI에게 원하는 것을 요청할 수 있는데, "영화 추천해줘"라고 하면 대개 평점/인기 상위 영화만 보여준다. 그 대신 사용자의 요청(장르/분위기/소재)에 맞춰 필터링해 추천하는 챗봇이 있으면 더 유용하겠다고 생각했다.

다만, 줄거리를 미리 알고 보는 것을 좋아하는 사람도 있지만 스포일러를 싫어하는 사람도 있기 때문에 스포일러 수위를 사용자가 조절할 수 있도록 했다.
그래서 기본적으로 스포일러 없이 알려주고, 결말과 줄거리를 명시적으로 요청하면 상세 내용까지 제공하도록 했다.

## ▶️ 실행 방법
1. 가상환경: `python3 -m venv .venv && source .venv/bin/activate`
2. 설치: `pip install -r requirements.txt`
3. API 설정: `.env` 생성 후 TMDB_TOKEN, GEMINI_API_KEY 입력
4. 데이터 수집: `python collect_data.py` (movies.jsonl이 이미 있다면 생략)
5. 인덱스 생성: `python build_index.py`
6. 챗봇 실행:
    - 바닐라 RAG: `python app.py`
    - LangChain: `python app_langchain.py`
    - LangGraph: `python app_langgraph.py`
#### LangSmith 추적
`.env`에 아래 항목을 추가하여 LangSmith 대시보드에서 체인 실행 과정을 추적
```
LANGSMITH_TRACING=true
LANGSMITH_API_KEY
LANGSMITH_PROJECT=movie-rag-chatbot
```

## 🐛 트러블슈팅
### 1. [데이터] 위키백과 줄거리 수집량 부족
- **문제**: `wikipedia` 라이브러리로 줄거리를 수집했더니 줄거리 양이 너무 적었다(169/500). 그 결과, "우주를 배경으로 한 SF 영화"를 검색해도 SF 장르 영화가 추천되지 않았다.
- **원인**: 대부분의 영화가 짧은 소개(overview)만 있었는데, overview는 홍보성 문구 위주라 "SF"같은 장르나 내용 키워드가 거의 없어서 의미 검색이 잘 되지 않았다. 또, `wikipedia` 라이브러리 자체가 오래돼서 응답이 불안정했다.
- **해결**: 라이브러리 대신 위키백과 공식 API를 직접 호출하는 방식으로 변경했다. `extracts`로 본문을 받아서 `== Plot ==` 부분만 잘라냈다.

### 2. [데이터] 위키백과 공식 API로 바꿨는데도 줄거리가 27개만 수집됨
- **문제**: 수정 후에 오히려 수집된 줄거리가 27개로 줄었다.
- **원인**: 응답 상태코드가 429(Too Many Requests)로, 요청을 너무 빠르게 많이 보내서 위키백과가 차단했다.
- **해결**: 429가 오면 `time.sleep(5)` 이후 최대 3번까지 재시도하고, 요청 간격도 0.5초로 늘렸다.
- **결과**: 248/500 줄거리 수집 성공. 유실 방지를 위해 `movies.jsonl`에 저장했다.

### 3. [검색] 특정 영화(예: 인셉션)를 검색하지 못함
- **문제**: "우주를 배경으로 한 SF 영화 추천"은 답을 잘 하지만, "인셉션 줄거리 알려줘"에는 데이터에 인셉션이 있음에도 불구하고 "정보가 없다"고 답했다.
- **원인**: 질문 문장 전체("인셉션 줄거리 결말까지")로 의미 검색을 해서 "줄거리, 결말" 같은 일반 단어에 밀려서 "인셉션"이라는 제목이 상위에 잡히지 않았다. 제목 기반 검색을 만들지 않아서 발생한 문제였다.
- **해결**: 제목 기반 검색을 추가했다. 질문에 등록된 영화 제목이 포함되면 그 제목으로 메타데이터 필터링(`where`)해서 해당 작품조각을 우선 검색한다.

### 4. [응답] 답변이 중간에 잘림
- **원인**: `max_tokens=1000` 제한 때문에 긴 줄거리 답변이 중간에 끊겼다.
- **해결**: `max_tokens=2000`으로 상향했다.

### 5. [환경] 구글로 마이그레이션
- Python 3.9 -> 3.11 업그레이드, 최신 `google-genai` 라이브러리로 전환
- 임베딩 및 답변 생성 모두 Gemini로 전환 후 검색 품질 개선 확인

### 6. [LangGraph] 제미나이 응답에서 텍스트 추출 오류
- **문제**: 분류 노드에서 `'list' object has no attribute 'lower'`에러 발생
- **원인**: 제미나이가 응답(`result.content`)을 문자열이  아니라 `[{'type': 'text', 'text': ...}]` 형태의 리스트로 반환하는 경우가 있었다.
- **해결**: 응답이 리스트일 때 각 조각에서 `text`만 추출해 합치도록 처리했다. 분류 노드(spoiler 판단)와 답변 생성 노드 양쪽에 동일하게 적용했다.

### 7. [LangGraph] 답변이 날것(raw) 형태로 출력됨
- **문제**: 답변 내용은 정상인데, `[{'type': 'text', 'text': '실제 답변', 'extras': {...}}]`처럼 리스트/딕셔너리 구조가 그대로 출력되었다.
- **원인**: 텍스트 추출 처리를 해놓고, 정작 반환할 때 정리된 변수가 아니라 원본 `result.content`를 반환하고 있었다.
- **해결**: 반환값을 정리된 텍스트 변수로 수정했다.

### 8. [LangGraph / 환경] 제미나이 무료 API 사용량 초과 (429)
- **문제**: 테스트 중 `429 RESURCE_EXHAUSTED` 에러 발생
- **원인**: 제미나이 무료 티어의 요청 한도를 초과했다. 특히 챗봇이 질문 1건당 요청을 2번 (스포일러 판단 + 답변 생성) 보내서 한도 소진이 빨랐다.
- **해결** 무료 한도가 더 넉넉한 모델로 잠시 교체해서 이용하고, 한도 초과 시 잠시 대기 후 재시도했다. 향후 분류 노드를 키워드 방식으로 바꿔 요청 수를 줄이는 방법도 있다.

## 📝 회고

### [바닐라 RAG 구현]

**배운 점**
- RAG가 검색(R) -> 증강(A) -> 생성(G) 구조라는 것을 직접 구현하며 이해했다.
    특히 임베딩 모델(검색)과 LLM(생성)이 서로 다른 역할을 하는 별개의 모델이라는 점, 검색은 텍스트를 벡터로 바꿔 유사도로 찾는다는 원리를 알게 됐다.
- 청킹, 메타데이터 태깅, 벡터 저장 같은 인덱싱 단계가 검색 품질을 좌우한다는 것을 체감했다

**어려웠던 점 & 해결**
- 위키백과 줄거리 수집이 라이브러리 불안정과 요청 차단으로 계속 실패했다.
    라이브러리 -> 공식 API -> 재시도 로직 순서로 원인을 좁혀가며 해결했다.
- ChromaDB가 구글 드라이브에서 손상되는 문제가 생겼는데 원인이 SQLite와 드라이브의 호환성 문제임을 파악하고 로컬 환경으로 옮겼다.
- 데이터가 부족해서 문제가 발생했다고 생각했는데 사실 검색을 못해서인 경우가 많았다.
    제목 인식 검색을 추가해서 특정 작품 검색 문제를 해결했다.

**깨달은 점**
- 처음에는 특정 장르 검색이 안 되는 이유가 하이브리드 검색을 적용하지 않아서라고 생각했다. 하지만 임베딩 모델을 무료 로컬 모델에서 Gemini 임베딩 모델로 바꾸니 검색 품질이 눈에 띄게 좋아졌다.
- 이를 통해, 검색 품질은 검색 방식 뿐만 아니라 텍스트를 벡터로 바꾸는 임베딩 모델의 성능에도 크게 좌우된다는 것을 알게 되었다. 좋은 검색 결과를 얻으려면 성능 좋은 임베딩 모델이 필요하다는 것을 직접 확인했다.

**아쉬운 점**
- 순수 의미 검색만으로는 장르 필터링이 정확하지 않아서 하이브리드 검색이나 리랭킹으로 개선할 여지가 있다.
- 답변 품질을 정량적으로 평가하지 못했다. (RAGAS 등)

**다음에 적용할 것**
- 검색 로직을 LangChain 리트리버로 마이그레이션하면서 하이브리드 검색도 함께 적용해볼 계획이다.

### [LangChain 마이그레이션]

**배운 점**
- 바닐라에서 함수로 직접 짰던 검색 -> 프롬프트 조합 -> 모델 호출 -> 텍스트 추출을 LangChain에서는 리트리버, 프롬프트, 모델, 파서라는 정해진 부품을 `|`로 이어붙인 체인으로 표현한다는 것을 이해했다.
- `|`는 앞 단계의 결과를 다음 단계로 넘긴다는 의미고, 바닐라에서 변수로 하나씩 넘기던 것을 자동화한 것임을 알게 되었다.

**느낀 점**
- 처음에는 LangChain 문법(`|`, RunnablePassthrough 등)이 복잡해 보였지만, 바닐라에서 개념을 먼저 학습하고 오니 같은 흐름을 더 짧게 표현한 것임을 알 수 있었다.
- 데잍를 그대로 재사용하고 검색과 답변 로직만 교체하면 돼서 파일을 역할별로 나눠둔 구조의 장점을 체감했다.

**깨달은 점**
- LangChain 버전에는 바닐라에 있던 제목 인식 검색과 스포일러 메타데이터 필터를 아직 옮기지 않았는데도, 특정 영화 검색과 스포일러 조절이 잘 동작했다.
- 원인을 분석해보니 2가지가 있었다.
    - 제목 검색: 임베딩 모델을 성능 좋은 Gemini로 교체해서 제목 필터 없이 순수 의미 검색만으로도 특정 영화를 잘 찾아냈다.
    - 스포일러 조절: 검색 단계에서 거르지는 않지만 시스템 프롬프트에 넣은 "명시적으로 요청할 때만 결말 포함"이라는 규칙에 따라 LLM이 스스로 스포일러를 조절했다.
- 같은 결과라도 구현 방식이 다른 것을 발견했다.
    - 바닐라: 검색 단계에서 메타데이터로 차단 (확실한 제어)
    - LangChain: LLM이 프롬프트 규칙으로 자제 (100%는 아님)
- 이를 통해 검색으로 제어, 프롬프트로 제어라는 설계 선택지가 있다는 것을 알게 되었다.

**다음에 적용할 것**
- LangGraph로 마이그레이션 후 AI Agent로 확장
- LangSmith Dataset 기반 정량 평가 - 최종 버전에 적용 예정
- 하이브리드 검색, LangSmith를 통한 체인 추적 및 평가
- 스포일러를 프롬프트 규칙이 아닌 메타데이터 필터로 더 엄격하게 제어

### [LangSmith 활용]
- LangSmith로 체인 실행을 추적하며 검색(retriever)이 실제로 어떤 영화 조각을 가져오고, 그것이 프롬프트에 어떻게 반영되는지 단계별로 확인할 수 있었다.
- 제목 필터가 없어도 특정 영화를 잘 찾는 현상을 추적 로그로 직접 검증할 수 있었다.
- 코드 내부를 눈으로 보니 동작의 원인을 이해하기 쉬웠다.

### [LangGraph 마이그레이션]

**배운 점**
- LangGraph는 State를 노드들이 주고받으며 처리하고, 조건부 엣지로 분기하는 구조라는 것을 이해했다. LangChain이 직선 파이프라면, LangGraph는 판단해서 길이 갈리는 그래프라는 차이를 알았다.
- 스포일러 조절을 바닐라 RAG처럼 코드로 판단하는 대신 분류 노드에서 LLM이 판단하도록 구현했다. 판단 로직이 실행부(app_langgraph.py)에서 그래프 안으로 들어가면서 역할이 깔끔해졌다.

**어려웠던 점**
- 처음엔 내 개인 프로젝트 챗봇이 단순해서 굳이 LangGraph가 필요 없다고 생각했지만, 스포일러 유무에 따라 검색 방식을 분기하는 구조로 만드니 그래프를 쓸 이유가 생겼다.
- 제미나이 응답 형식(리스트/문자열)이 일정하지 않아 텍스트 추출을 별도로 처리해야 하는 문제가 있었다.

**다음에 적용할 것**
- 의도 분류(추천, 특정 작품, 잡담) 등의 분기도 추가해서 에이전트를 더 확장
- 분류 노드를 키워드 방식으로 바꿔 API 요청 수 줄여 한도 관리
- LangSmith Dataset 기반 정량 평가
